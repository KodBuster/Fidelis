# Регистрация B2B и личный кабинет

## Настройка перед запуском

1. Node.js 22 или новее. Dockerfile, Amvera и Render настроены на 22.
2. По решению заказчика доступ открывается группе «Оптовик» (ID 2): `ADVANTSHOP_APPROVED_GROUP_ID=2`, `ADVANTSHOP_APPROVED_GROUP_NAME=Оптовик`. Группа не должна назначаться новым покупателям автоматически. Удаление покупателя из неё закрывает доступ при следующем запросе. В API группы указана скидка 50%; текущие цены витрины сохраняются, персональные скидки этим изменением не внедряются.
3. Задать `SITE_URL=https://fidelischina.ru` — публичный HTTPS-адрес Фиделис без завершающего слеша. Он используется для ссылок в письмах и проверки Origin.
4. Задать `SMTP_PASSWORD` реальным паролем SMTP/паролем приложения Rambler. Строка `*****` не является паролем. Прочие SMTP-параметры и четыре адреса уведомлений имеют указанные заказчиком значения по умолчанию (см. `.env.example`). На порту 587 используется обязательный STARTTLS с проверкой сертификата, на 465 — TLS с начала соединения. IMAP не используется.
5. `AUTH_DB_PATH=/data/fidelis-auth.sqlite` должен находиться на постоянном диске. Amvera уже монтирует `/data`. Для Docker нужен volume `/data`; для Render требуется подключить persistent disk `/data`. Запускать одну реплику приложения. Не использовать локальный SQLite на эфемерном или общем сетевом диске; для нескольких реплик потребуется перенос хранилища в общую СУБД.
6. Проверить, что `ADVANTSHOP_BASE_URL` и оба API-ключа относятся к нужному магазину. Требуются Server API: customers, customergroups, order/getlist, order/add. Ключи никогда не передаются браузеру.
7. Настроить внешний reverse proxy так, чтобы он перезаписывал `X-Forwarded-For` достоверным адресом клиента. Ограничения попыток по email работают независимо от IP.

Без SMTP-пароля, SITE_URL и группы доступа регистрация отвечает о временной недоступности. Каталог по умолчанию закрыт; публичного переключателя обхода нет.

## Порядок регистрации

Пользователь заполняет имя, телефон, email, организацию, город, пароль (10–128 символов), повтор пароля и согласие. Пароль хранится только как scrypt-хеш с индивидуальной солью. На email отправляется одноразовая ссылка на 24 часа. Открытие ссылки показывает страницу с кнопкой подтверждения: почтовый сканер не подтверждает адрес GET-запросом.

После подтверждения email сервер создаёт покупателя в AdvantShop. Если там уже есть покупатель с точно таким подтверждённым email, используется его ID. В существующей карточке не перезаписываются реквизиты и группа. При конфликте телефона/ошибке API синхронизация повторяется; пароль и сессия при этом не теряются.

Администраторы получают анкету со ссылкой на покупателя после подтверждения email и успешной синхронизации. В админке нужно назначить группу доступа. Сайт проверяет группу непосредственно через API без общего кеша прав. Фоновый обработчик каждую минуту проверяет подтверждённые аккаунты и ставит письмо об одобрении в очередь. Если процесс был выключен, проверка продолжится после запуска. Ссылка карточки использует стандартный путь `/adminv3/customers/edit/{id}`; при другой версии админки найти покупателя по указанным в письме email/ID.

## Кабинет и заказы

Вход по email и паролю. Сессия — случайный токен в HttpOnly cookie, в БД только его SHA-256-хеш; срок 14 дней. Для сброса пароля одноразовая ссылка на 1 час. После сброса/смены пароля старые сессии удаляются. Реквизиты показаны в кабинете; для изменения пользователь обращается к менеджеру, чтобы не обходить проверку организации.

Новые заказы содержат `OrderCustomer.CustomerId`, email и организацию аккаунта. История запрашивается в Server API с фильтром `CustomerId`, дополнительно проверяется владелец каждой записи. Данные администраторских комментариев не передаются в кабинет. Старые заказы отображаются только если уже привязаны к тому же ID в AdvantShop; произвольный поиск по email/телефону не используется.

Гостям и ожидающим одобрения недоступны коллекции, цены, категории, карточки товаров, поиск, избранное, сравнение, корзина и оформление. На главной публичная проекция категорий содержит только название, число моделей и до трёх случайных уникальных фото из этой категории AdvantShop. Успешные выборки обновляются раз в пять минут и кешируются отдельно по категориям. Если фото меньше трёх — показываются имеющиеся; если их нет — текст «Фото скоро появятся». При ошибке API количество помечается как временно недоступное; демонстрационные товары, ложный ноль и чужие обложки не подставляются. Количество означает число уникальных моделей со всех страниц категории, а не сумму складских остатков. Для проверки реального источника и каждой фотографии запустить `node scripts/verify-live-category-previews.mjs` при работающем локальном сайте и доступе к сети.

## Эксплуатация

Письма сохраняются в SQLite и повторяются при ошибках SMTP с увеличением интервала до часа. Письма отправляются отдельно каждому администратору. Очередь сохраняется при перезапуске. SMTP может повторно доставить письмо при сбое между доставкой и удалением записи; используется стабильный Message-ID. Ошибки синхронизации логируются без паролей и тела писем.

Резервировать SQLite штатным online backup API (например, `better-sqlite3.backup()`), а не копировать только `.sqlite` без WAL при работающем приложении. Хранить резервные копии с ограниченным доступом: база содержит персональные данные, хеши паролей и одноразовые ссылки в очереди.

Production собирается командой `next build --webpack`, чтобы не зависеть от хешированных имён нативных модулей Turbopack. Пакет `better-sqlite3` явно включается в `amvera-bundle/node_modules`. В конце сборки и перед запуском проверяется загрузка нативного SQLite в памяти. В журнале актуальной сборки должна быть строка `Amvera runtime check OK: webpack-sqlite-v2` с версией Node, платформой и временем упаковки. Если после нового деплоя всё ещё виден `better-sqlite3-90e2652d1716b047`, сверить коммит и лог сборки: в актуальном production-коде хешированный импорт не используется. Переход не меняет путь постоянной базы `/data/fidelis-auth.sqlite`.

Проверки: `npm run build`, `npx tsc --noEmit`, `node scripts/test-b2b-auth.mjs` (локальный AdvantShop-макет, изолированная БД; реальным адресатам ничего не отправляется). Для проверки готового standalone-сервера задать `AUTH_TEST_PRODUCTION=1` перед запуском теста. `npm run test:amvera` проверяет переносимость ссылок и запускает полные проверки регистрации на копии `amvera-bundle` вне репозитория, без доступа к зависимостям исходного проекта. Упаковщик копирует зависимости с разыменованием ссылок Turbopack, чтобы артефакт не ссылался на `node_modules` сборочного контейнера. Перед публикацией отдельно проверить реальный SMTP, реальные API магазина и карточку покупателя в админке.
